# AskVUZ

Сервис вопросов-ответов в реальном времени для чат-бота МАХ: студент выбирает
вуз → выбирает категорию вопроса (Поступление, Учебный процесс, Заказ справок
и т.д.) → задаёт вопрос → вопрос маршрутизируется специалисту вуза с
подходящей ролью → ответ приходит в реальном времени, диалог можно продолжать
(уточняющие вопросы), затем оценить и закрыть. Отвечающему за это начисляется
**аура** — очки репутации, от которых зависит его роль (Помощник → Знаток →
Профи).

Хакатон «Образовательные решения» (Минобрнауки России × МАХ).

## Архитектура

```
┌──────────────┐      webhook       ┌───────────────────────────────┐
│   МАХ (бот)  │ ─────────────────▶ │           backend               │
│ мобильный/веб│ ◀───────────────── │ Express + Socket.IO              │
└──────────────┘   sendMessage       │  - conversation engine (визард)  │
                                      │  - треды вопросов и сообщений    │
┌──────────────┐   REST + WS         │  - маршрутизация по роли         │
│  frontend     │ ◀────────────────▶ │  - аура / роли                   │
│ - ЛК студента │                     │  - SQLite (better-sqlite3)       │
│ - инбокс      │                     └───────────────────────────────┘
│   эксперта    │
│ - админ-панель│
│ - рейтинг     │
└──────────────┘
```

Ядро продукта — `backend/src/conversation/engine.ts`: визард выбора
вуза/категории/вопроса, общий для обоих транспортов:

- реального МАХ (`backend/src/max/webhook.ts` + `backend/src/max/client.ts`).
  Студент в МАХ ничего не логинит — его аккаунт (`Student`) создаётся
  автоматически по `sender.user_id` платформы;
- веб-приложения (`backend/src/routes/student.ts` →
  `frontend/src/pages/AskQuestion.tsx`) — тот же визард, студент входит по
  имени (см. [«Как войти»](#как-войти) и [ограничения MVP](#известные-ограничения-mvp)).

После того как вопрос создан, вся дальнейшая переписка (ответ специалиста,
уточняющие вопросы, повторные ответы) идёт через треды сообщений
(`backend/src/db/store.ts` → таблица `messages`), а не через сам визард —
поэтому и МАХ-диалог, и веб-кабинет одинаково поддерживают продолжение
разговора.

## Быстрый старт (Docker)

```bash
cp .env.example .env
docker compose up --build
```

- Backend: http://localhost:4000 (REST API, health-check `/health`, MAX
  webhook `/webhook/max`)
- Frontend (личный кабинет студента / инбокс эксперта / админ-панель /
  рейтинг): http://localhost:5173

При первом запуске (`SEED_ON_START=true` по умолчанию) backend автоматически
создаёт демо-данные: 2 тестовых вуза, категории вопросов, платформенного
администратора и экспертов на всех 3 ступенях роли. Список учёток — см.
[Тестовые учётные записи](#тестовые-учётные-записи).

## Где хранятся данные

Backend хранит все данные (вузы, категории, студентов, вопросы, сообщения,
ауру) в одном файле SQLite, без внешней СУБД.

- В Docker: путь внутри контейнера — `/app/data/askvuz.db`, и он
  bind-mount'ится на хост в `docker-compose.yml` как
  `./backend/data/askvuz.db` — то есть после `docker compose up` в папке
  проекта появится файл `backend/data/askvuz.db`, который можно открыть
  напрямую (например, приложением «DB Browser for SQLite» или командой
  `sqlite3 backend/data/askvuz.db`).
- Без Docker (`npm run dev` в `backend/`): файл лежит в
  `backend/data/askvuz.db` — создаётся автоматически при первом запуске.
- Путь настраивается переменной окружения `DATABASE_FILE` (см.
  `backend/src/db/connection.ts`).

## Как войти

Приложение различает два независимых типа входа.

**Студент** — на главной странице (`/`) вводит только имя. Это создаёт (или,
при повторном входе тем же именем, находит существующую) запись `Student` и
выдаёт токен, который сохраняется в браузере. Отдельного пароля у студента в
MVP нет — см. [ограничения MVP](#известные-ограничения-mvp).

**Сотрудник вуза** (эксперт, администратор вуза, платформенный
администратор) входит по e-mail и паролю на странице `/login` — ссылка
«Войти» есть в шапке сайта на любой странице, а также прямой ссылкой внизу
формы входа студента.

Учётные данные нового сотрудника создаются один раз и показываются в
интерфейсе сразу после создания аккаунта:

- когда платформенный администратор подключает новый вуз (раздел
  «Платформенный админ» в админ-панели) — вместе с вузом сразу создаётся его
  первый администратор, e-mail и временный пароль показываются в том же
  окне;
- когда администратор вуза приглашает нового отвечающего (раздел
  «Пригласить нового отвечающего») — e-mail и временный пароль показываются
  сразу после отправки формы.

В обоих случаях это демо-режим: в реальном продукте временный пароль
отправлялся бы приглашением на почту, а не показывался в интерфейсе.

## Пользовательские сценарии

**Студент** (по умолчанию, без входа): открывает сервис → вводит имя → видит
две кнопки: «Задать вопрос» и «Мои вопросы».

*Задать вопрос* — визард: вуз → категория → текст вопроса. После отправки
студент сразу может перейти в «Мои вопросы».

*Мои вопросы* — личный кабинет: список всех вопросов студента со статусами
(«Ожидает специалиста», «Взят в работу», «Есть ответ», «Закрыт»). Открыв
вопрос, студент видит весь тред сообщений и может:

- написать уточняющий вопрос специалисту (диалог продолжается);
- оценить ответ («Решило вопрос» / «Помогло» / «Не помогло») — это начисляет
  ауру отвечавшему;
- закрыть вопрос кнопкой «Закрыть вопрос», если он больше не актуален —
  дальше он не отображается в очереди у экспертов, переписка блокируется.

**Отвечающий (эксперт)**: входит на `/login` → «Мои вопросы» → видит два
списка: «Новые» (доступные его роли и категории, никем не взятые) и «В
работе у вас» (уже взятые им, независимо от статуса). Открыв вопрос, можно
взять его в работу и отвечать — в том числе на уточняющие вопросы студента,
диалог идёт в том же треде.

**Администратор вуза**: подключает категории вопросов, приглашает
отвечающих, вручную назначает роль, может удалить отвечающего (аккаунт
деактивируется — переписка и начисленная аура сохраняются) или категорию.

**Платформенный администратор**: подключает новые вузы к сервису; при
подключении вуза сразу создаётся аккаунт его администратора.

**Рейтинг** — публичная страница (доступна и студентам, и всем без входа):
выбор вуза → таблица отвечающих с их ролью и аурой. У студента и анонимного
посетителя по умолчанию открыт первый вуз из списка; у вошедшего сотрудника
по умолчанию открыт его собственный вуз.

## Роли и аура

Отвечать могут не все — только верифицированные вузом пользователи
(`isAnswerer = true`), приглашённые через админ-панель. Роль растёт
автоматически по накопленной ауре:

| Роль      | Мин. аура | Комментарий                             |
|-----------|-----------|------------------------------------------|
| Помощник  | 0         | стартовая роль после верификации вузом    |
| Знаток    | 150       |                                            |
| Профи     | 600       | высшая роль, ответ считается самым ценным |

Начисление ауры (`backend/src/reputation.ts`) происходит только в момент,
когда студент оценивает ответ (`/student/questions/:id/rate`) — сам факт
ответа эксперта ничего не начисляет:

- ответ отмечен «решило вопрос полностью» — **+25**
- ответ отмечен «помогло» — **+10**
- к этому, если первый ответ пришёл быстро (< 5 минут, настраивается
  `FAST_RESPONSE_THRESHOLD_SECONDS`) и студент поставил «решило»/«помогло» —
  ещё **+5**
- ответ отмечен «не помогло» — **−5**

### Доступ к категориям

Два независимых правила, оба обязательны:

1. **Минимальная роль категории** (`Category.minRole`) — порог по лестнице
   Помощник → Знаток → Профи. Роль выше порога тоже подходит: Профи видит
   все категории вуза.
2. **Флаг «конфиденциально»** (`Category.isSensitive`) — по умолчанию
   выключен; включён для категории психологической поддержки/безопасности.
   Такую категорию видят только сотрудники вуза (`isStaff = true`), даже
   если у волонтёра уже роль Профи по ауре — доступ к чувствительным
   обращениям требует официального статуса сотрудника, назначаемого вузом
   вручную при приглашении, а не только активности.

Это два ортогональных правила, а не одна шкала: «сколько вопросов успешно
закрыто» (аура/роль) и «официальный ли статус сотрудника вуза» (isStaff)
измеряют разные вещи. Итоговая матрица по конкретному вузу видна в панели
администратора вуза, раздел «Роли и доступ к категориям».

## Проверка решения без токена МАХ

На момент сборки решения у команды не было развёрнутого рабочего токена
чат-бота МАХ (токен выдают организаторы отдельно). Веб-приложение
(`frontend/`) проходит тот же пользовательский сценарий через тот же
backend-код (`conversation/engine.ts`), что и реальный МАХ-бот — отличается
только транспорт. Это явно помеченный тестовый режим (`MOCK_MAX=true` по
умолчанию).

1. Откройте http://localhost:5173, введите имя — откроется личный кабинет
   студента.
2. «Задать вопрос» → выберите вуз → категорию → напишите вопрос.
3. В другой вкладке/браузере войдите как эксперт (`pro@itmo.demo` /
   `demo12345`) → «Мои вопросы» → возьмите вопрос в работу и ответьте.
4. Вернитесь на вкладку студента → «Мои вопросы» — ответ уже там. Напишите
   уточняющий вопрос, оцените ответ, при желании закройте вопрос.
5. На «Рейтинг» видно, как выросла аура эксперта и, если порог пройден,
   изменилась его роль.

## Запуск в МАХ

1. В `.env` установите `MOCK_MAX=false` и `MAX_BOT_TOKEN=<токен>`.
2. Зарегистрируйте у МАХ webhook-адрес `https://<ваш-домен>/webhook/max`
   (опционально защитите его общим секретом через `MAX_WEBHOOK_SECRET`).
3. Перезапустите backend.

Пути `POST /messages` / `POST /answers` в `backend/src/max/client.ts` и
формат `update_type` в `backend/src/max/webhook.ts` написаны по
общепринятым конвенциям ботовых API такого типа — перед подключением
реального токена сверьте их с актуальной документацией MAX Bot API.
Остальная часть системы (маршрутизация, аура, БД, фронтенд) от этих деталей
не зависит.

В МАХ студент не логинится отдельно — его `Student`-запись создаётся
автоматически по `sender.user_id` из платформы (`students.findOrCreateByMaxUserId`
в `backend/src/db/store.ts`). Отдельный экран «войдите по имени» — только
для веб-версии.

## Переменные окружения

См. `.env.example` в корне (для `docker compose`) и `backend/.env.example` /
`frontend/.env.example` (для запуска без Docker).

| Переменная            | Назначение                                                                |
|-------------------------|-----------------------------------------------------------------------------|
| `MOCK_MAX`             | `true` (по умолчанию) — не звать реальный MAX Bot API                       |
| `MAX_BOT_TOKEN`        | токен бота МАХ (выдают организаторы)                                        |
| `MAX_WEBHOOK_SECRET`   | опциональный секрет для проверки входящих вебхуков                          |
| `JWT_SECRET`           | секрет для подписи JWT (обязательно заменить вне локальной демонстрации)    |
| `SEED_ON_START`        | заполнять ли БД демо-данными при старте контейнера                          |
| `DATABASE_FILE`        | путь к файлу SQLite (см. [«Где хранятся данные»](#где-хранятся-данные))     |

Секреты, токены и пароли нигде в коде не захардкожены — только читаются из
переменных окружения; `.env` — в `.gitignore`/`.dockerignore`, в репозиторий
передаётся только `.env.example` без реальных значений.

## Известные ограничения MVP

- Вход студента — по имени, без пароля. Повторный вход тем же именем
  (без учёта регистра) находит существующую запись `Student`, постоянство
  сессии обеспечивает JWT-токен в браузере. В реальном продукте вход был бы
  по логину/паролю (или, в МАХ, автоматически через платформенный `user_id`
  — уже реализовано для канала МАХ, см. `students.findOrCreateByMaxUserId`),
  а вуз указывался бы один раз при регистрации.
- Данные тестовые — оба вуза, все категории и все учётные записи экспертов
  заранее подготовлены сид-скриптом (`backend/src/db/seed.ts`).
- Интеграция с МАХ подготовлена, но не подключена к реальному боту —
  причина в отсутствии токена на момент сборки решения. Код вебхука и
  клиента написан и готов к подключению, см. [«Запуск в МАХ»](#запуск-в-мах).
- Только студенты задают вопросы — роль «абитуриент» не реализована.
- Базовый фильтр вопросов от спама (`backend/src/moderation.ts`) — не
  полноценная система модерации: постоянного чёрного списка студентов и
  ограничения «не больше N вопросов в час» пока нет.
- Нет интеграции с реальными системами вуза (деканат/1С).
- Пароли для демо-аккаунтов эксперта/админа заведомо простые и находятся в
  этом README — только для локальной проверки решения, не для продакшена.
