# AskVUZ

Сервис вопросов-ответов в реальном времени для чат-бота МАХ: студент выбирает
вуз → выбирает категорию вопроса (Поступление, Учебный процесс, Заказ справок
и т.д.) → задаёт вопрос → вопрос маршрутизируется онлайн-специалисту вуза с
подходящей ролью → ответ приходит в реальном времени, диалог можно продолжать
(уточняющие вопросы), затем оценить и закрыть. Отвечающему за это начисляется
**аура** — очки репутации, от которых зависит его роль (Помощник → Знаток →
Профи).

Хакатон «Образовательные решения» (Минобрнауки России × МАХ).

## Что изменилось после первой версии

По итогам ревью реализовано (см. историю правок в конце файла, если нужно
сослаться на конкретный пункт):

- вопрос теперь хранит **весь тред сообщений**, а не одну пару вопрос-ответ:
  можно продолжать диалог со специалистом, отвечать несколько раз;
- у каждого вопроса есть кнопка **«Закрыть вопрос»** (студент);
- у студентов есть **личный кабинет**: вход по имени, раздел «Мои вопросы» со
  всей историей и статусами, отдельная кнопка «Задать вопрос»;
- у отвечающего баг «взял в работу → вопрос пропал» **исправлен**: теперь
  claim переводит вопрос в раздел «В работе у вас», и по нему можно отвечать
  и продолжать переписку;
- очки репутации переименованы в **ауру**;
- вкладка «Рейтинг» **публична** — доступна и студентам, не только отвечающим;
- задавать вопросы могут **только вошедшие студенты** (без анонимного чата и
  без роли «абитуриент» — по объёму MVP она не нужна);
- ролей теперь **три**: Помощник, Знаток, Профи;
- в README чётко указано, где физически лежит файл базы данных.

## Что исправлено во второй волне правок

- **вход студента был неидемпотентным**: `/api/student/login` создавал
  НОВУЮ запись `Student` при каждом входе, поэтому после выхода и повторного
  входа под тем же именем «Мои вопросы» оказывались пустыми — казалось, что
  вопросы удаляются. Теперь повторный вход с тем же именем (без учёта
  регистра, включая кириллицу — см. комментарий в `db/store.ts`, почему
  обычный SQL `lower()` для кириллицы не работал) возвращает того же
  студента и всю его историю;
- **аура начислялась сразу при ответе эксперта**, а не после оценки
  студентом. Теперь весь начисление ауры (включая бонус за быстрый ответ)
  происходит только в момент оценки (`/student/questions/:id/rate`) — до
  этого аура эксперта не меняется;
- **«зависшие» кнопки визарда** могли сбивать диалог: в истории чата все
  кнопки предыдущих шагов оставались кликабельными, и клик по старой кнопке
  (например, категории из позапрошлого сообщения) расходился с реальным
  шагом на сервере — бот в ответ откатывал весь диалог к «выберите вуз».
  Теперь кликабельны только кнопки последнего сообщения бота, у более
  ранних кнопки визуально отключены;
- добавлен **разумный ответ по умолчанию**, если выбранная категория вдруг
  недоступна («категория больше недоступна, начнём заново» вместо тихого
  сброса без объяснения);
- в личном кабинете студента и в кабинете эксперта список вопросов раньше
  полагался только на WebSocket-пуш — если сокет обрывался (что и
  происходило из-за пересоздания соединения при каждом клике по вопросу),
  новые сообщения не приходили вообще. Теперь для обеих страниц есть
  fallback-опрос сервера раз в 5–8 секунд, а само сокет-соединение
  переиспользуется, а не пересоздаётся на каждый клик;
- добавлен **базовый фильтр вопросов** от спама/мусора (слишком короткий
  или слишком длинный текст, флуд повторяющимся символом, несколько ссылок
  подряд, короткий стоп-лист слов) — простая защита, чтобы у экспертов не
  копился спам. Это не полноценная система модерации: постоянного
  чёрного списка студентов и ограничения «не больше N вопросов в час» пока
  нет — see `backend/src/moderation.ts` (комментарий там же описывает, что
  нужно добавить для полноценной защиты — таблицу `banned_students` и
  admin-действие «заблокировать студента»).

## Архитектура

```
┌──────────────┐      webhook       ┌───────────────────────────────┐
│   МАХ (бот)  │ ─────────────────▶ │           backend               │
│ мобильный/веб│ ◀───────────────── │ Express + Socket.IO              │
└──────────────┘   sendMessage       │  - conversation engine (визард)  │
                                      │  - треды вопросов и сообщений    │
┌──────────────┐   REST + WS         │  - маршрутизация по роли         │
│  frontend     │ ◀────────────────▶ │  - аура / роли                   │
│ - ЛК студента │                     │  - SQLite (better-sqlite3)       │
│ - инбокс      │                     └───────────────────────────────┘
│   эксперта    │
│ - админ-панель│
│ - рейтинг     │
└──────────────┘
```

Ядро продукта — **`backend/src/conversation/engine.ts`**: визард выбора
вуза/категории/вопроса, общий для обоих транспортов:

- **реального МАХ** (`backend/src/max/webhook.ts` + `backend/src/max/client.ts`).
  Студент в МАХ ничего не логинит — его аккаунт (`Student`) создаётся
  автоматически по `sender.user_id` платформы;
- **веб-приложения** (`backend/src/routes/student.ts` →
  `frontend/src/pages/AskQuestion.tsx`) — тот же визард, но студент явно
  «входит» по имени (см. [ограничения MVP](#известные-ограничения-mvp)).

После того как вопрос создан, вся дальнейшая переписка (ответ специалиста,
уточняющие вопросы, повторные ответы) идёт через треды сообщений
(`backend/src/db/store.ts` → таблица `messages`), а не через сам визард —
поэтому и МАХ-диалог, и веб-кабинет одинаково поддерживают продолжение
разговора.

## Быстрый старт (Docker)

```bash
cp .env.example .env
docker compose up --build
```

- Backend: http://localhost:4000 (REST API, health-check `/health`, MAX
  webhook `/webhook/max`)
- Frontend (личный кабинет студента / инбокс эксперта / админ-панель /
  рейтинг): http://localhost:5173

При первом запуске (`SEED_ON_START=true` по умолчанию) backend автоматически
создаёт демо-данные: 2 тестовых вуза, категории вопросов, платформенного
администратора и экспертов на всех 3 ступенях роли. Список учёток — см.
[Тестовые учётные записи](#тестовые-учётные-записи).

Сборка обоих образов укладывается в лимит 5 минут (без учёта первой загрузки
базовых образов node:20-alpine / nginx:1.27-alpine).

## Где хранятся данные

Backend хранит все данные (вузы, категории, студентов, вопросы, сообщения,
ауру) в **одном файле SQLite**, без внешней СУБД.

- **В Docker**: путь внутри контейнера — `/app/data/askvuz.db`, и он
  **bind-mount'ится на хост** в `docker-compose.yml` как
  `./backend/data/askvuz.db` — то есть после `docker compose up` в папке
  проекта появится файл `backend/data/askvuz.db`, который можно открыть
  напрямую (например, приложением «DB Browser for SQLite» или командой
  `sqlite3 backend/data/askvuz.db`).
- **Без Docker** (`npm run dev` в `backend/`): файл лежит в
  `backend/data/askvuz.db` — создаётся автоматически при первом запуске.
- Путь настраивается переменной окружения `DATABASE_FILE` (см.
  `backend/src/db/connection.ts`).

Это обычный однофайловый SQLite — никакой отдельный сервер БД не нужен, что и
позволяет вложиться в 5-минутный лимит сборки Docker-образа.

## Пользовательские сценарии

**Студент** (по умолчанию, без входа): открывает сервис → вводит имя (это и
есть «вход» в MVP) → видит две кнопки: «Задать вопрос» и «Мои вопросы».

*Задать вопрос* — тот самый визард: вуз → категория → текст вопроса. После
отправки студент сразу может перейти в «Мои вопросы».

*Мои вопросы* — личный кабинет: список всех вопросов студента со статусами
(«Ожидает специалиста», «Взят в работу», «Есть ответ», «Закрыт»). Открыв
вопрос, студент видит весь тред сообщений, может:
- написать уточняющий вопрос специалисту (диалог продолжается);
- оценить ответ («Решило вопрос» / «Помогло» / «Не помогло») — это начисляет
  ауру отвечавшему;
- закрыть вопрос кнопкой «Закрыть вопрос», если он больше не актуален —
  дальше он не отображается в очереди у экспертов и переписка блокируется.

**Отвечающий (эксперт)**: входит по e-mail/паролю (кнопка «Войти» в шапке) →
«Мои вопросы» → видит два списка: «Новые» (доступные его роли и категории,
никем не взятые) и «В работе у вас» (уже взятые им, независимо от статуса —
специально исправлено, чтобы «Взять в работу» не «пряталo» вопрос, а
переводило его в рабочий тред). Открыв вопрос, можно взять его в работу и
отвечать — в том числе на уточняющие вопросы студента, диалог тот же тред.

**Администратор вуза**: подключает категории вопросов, приглашает
отвечающих, вручную назначает роль (например, штатному сотруднику деканата).

**Платформенный администратор**: подключает новые вузы (организации) к
сервису.

**Рейтинг** — публичная страница (доступна и студентам, и всем без входа):
выбор вуза → таблица отвечающих с их ролью и аурой.

## Как проверить основной сценарий без токена МАХ

На момент сборки решения у команды не было развёрнутого рабочего токена
чат-бота МАХ (токен выдают организаторы отдельно — Ограничения, п.9 брифа).
Веб-приложение (`frontend/`) проходит **тот же самый** пользовательский
сценарий через **тот же самый backend-код**
(`conversation/engine.ts`), что и реальный МАХ-бот — отличается только
транспорт. Это явно помеченный тестовый режим согласно Ограничению п.10
брифа (`MOCK_MAX=true` по умолчанию).

1. Откройте http://localhost:5173, введите имя — это откроет личный кабинет
   студента.
2. «Задать вопрос» → выберите вуз → категорию → напишите вопрос.
3. В другой вкладке/браузере войдите как эксперт (например `pro@itmo.demo` /
   `demo12345`) → «Мои вопросы» → возьмите вопрос в работу и ответьте.
4. Вернитесь на вкладку студента → «Мои вопросы» — ответ уже там (доставлен
   через WebSocket в реальном времени). Напишите уточняющий вопрос, оцените
   ответ, при желании закройте вопрос.
5. На «Рейтинг» видно, как выросла аура эксперта и, если порог пройден,
   изменилась его роль.

## Подключение к МАХ

Когда организаторы выдадут рабочий токен бота:

1. В `.env` установите `MOCK_MAX=false` и `MAX_BOT_TOKEN=<токен>`.
2. Зарегистрируйте у МАХ webhook-адрес `https://<ваш-домен>/webhook/max`
   (опционально защитите его общим секретом через `MAX_WEBHOOK_SECRET`).
3. Перезапустите backend.

**Важно:** пути `POST /messages` / `POST /answers` в
`backend/src/max/client.ts` и формат `update_type` в
`backend/src/max/webhook.ts` написаны по общепринятым конвенциям ботовых API
такого типа. Перед подключением реального токена сверьте их с актуальной
документацией MAX Bot API — бриф сам предупреждает, что документация МАХ
развивается и обновляется. Остальная часть системы (маршрутизация, аура,
БД, фронтенд) от этих деталей не зависит.

В МАХ студент не логинится отдельно — его `Student`-запись создаётся
автоматически по `sender.user_id` из платформы (см. `students` в
`backend/src/db/store.ts`, `findOrCreateByMaxUserId`). Отдельный экран
«войдите по имени» — только для веб-версии, где такого готового
идентификатора нет (см. [ограничения MVP](#известные-ограничения-mvp)).

## Роли и аура

Отвечать могут не все — только верифицированные вузом пользователи
(`isAnswerer = true`), приглашённые через админ-панель. Роль растёт
автоматически по накопленной ауре:

| Роль        | Мин. аура | Комментарий                                      |
|-------------|-----------|---------------------------------------------------|
| Помощник    | 0         | стартовая роль после верификации вузом            |
| Знаток      | 150       |                                                     |
| **Профи**   | 600       | высшая роль, ответ считается самым ценным          |

Начисление ауры (`backend/src/reputation.ts`):

- ответ отмечен «решило вопрос полностью» — **+25**
- ответ отмечен «помогло» — **+10**
- быстрый первый ответ (< 5 минут, настраивается
  `FAST_RESPONSE_THRESHOLD_SECONDS`) — **+5**
- ответ отмечен «не помогло» — **−5**

Категории вопросов сами задают минимальную роль для ответа
(`Category.minRole`), а «чувствительные» категории (психологическая
поддержка/безопасность) дополнительно доступны только сотрудникам вуза
(`isStaff = true`) — так продукт не подменяет профессиональную помощь
специалиста, а маршрутизирует к нему. Сотрудников вуза администратор может
назначить на роль вручную — это не отменяет автоматический рост по ауре для
остальных отвечающих.

## Тестовые учётные записи

Создаются сид-скриптом (`backend/src/db/seed.ts`) при `SEED_ON_START=true`.
Пароль для всех, кроме платформенного админа: **`demo12345`**.

| Роль                              | E-mail                  | Вуз                     |
|-----------------------------------|--------------------------|--------------------------|
| Платформенный админ               | `admin@askvuz.local` / `admin12345` | — (все вузы) |
| Админ вуза                        | `uniadmin@itmo.demo`     | ИТМО (демо)              |
| Помощник                          | `helper@itmo.demo`       | ИТМО (демо)              |
| Знаток                            | `knower@itmo.demo`       | ИТМО (демо)              |
| Профи (сотрудник, зам. декана)    | `pro@itmo.demo`          | ИТМО (демо)              |
| Помощник                          | `helper@susu.demo`       | ЮУрГУ (демо)             |
| Профи (сотрудник, приёмная комиссия) | `pro@susu.demo`      | ЮУрГУ (демо)             |

Студенты отдельных тестовых аккаунтов не имеют — «вход» создаёт новую запись
по любому введённому имени (см. [ограничения MVP](#известные-ограничения-mvp)).

## Переменные окружения

См. `.env.example` в корне (для `docker compose`) и `backend/.env.example` /
`frontend/.env.example` (для запуска без Docker). Ключевые:

| Переменная            | Назначение                                                        |
|------------------------|--------------------------------------------------------------------|
| `MOCK_MAX`             | `true` (по умолчанию) — не звать реальный MAX Bot API              |
| `MAX_BOT_TOKEN`        | токен бота МАХ (выдают организаторы)                              |
| `MAX_WEBHOOK_SECRET`   | опциональный секрет для проверки входящих вебхуков                |
| `JWT_SECRET`           | секрет для подписи JWT (обязательно заменить вне локальной демонстрации) |
| `SEED_ON_START`        | заполнять ли БД демо-данными при старте контейнера                |
| `DATABASE_FILE`        | путь к файлу SQLite (см. [«Где хранятся данные»](#где-хранятся-данные)) |

Секреты, токены и пароли нигде в коде не захардкожены — только читаются из
переменных окружения; `.env` — в `.gitignore`/`.dockerignore`, в репозиторий
передаётся только `.env.example` без реальных значений.

## Известные ограничения MVP

- **Вход студента — по имени, без пароля.** Каждый «вход» создаёт новую
  запись `Student`, а постоянство сессии обеспечивает JWT-токен, сохранённый
  в браузере (localStorage). Это осознанное упрощение MVP: в реальном
  продукте вход был бы по логину/паролю (или, в МАХ, автоматически через
  платформенный `user_id` — что уже реализовано для канала МАХ, см.
  `students.findOrCreateByMaxUserId`), а вуз указывался бы один раз при
  регистрации, а не выбирался при каждом вопросе.
- **Данные тестовые.** Оба вуза, все категории и все учётные записи
  экспертов — заранее подготовленные демо-данные (`backend/src/db/seed.ts`).
- **Интеграция с МАХ подготовлена, но не подключена к реальному боту** —
  причина исключительно в отсутствии токена на момент сборки решения (токен
  выдают организаторы отдельно). Код вебхука и клиента написан и готов к
  подключению — см. [«Подключение к МАХ»](#подключение-к-мах).
- **Только студенты задают вопросы.** Роль «абитуриент» (не студент вуза) не
  реализована — по объёму MVP решили сфокусироваться на одном сегменте
  пользователей, как и рекомендует бриф («не выбирайте слишком широкую
  аудиторию»).
- Нет интеграции с реальными системами вуза (деканат/1С) — вне рамок MVP.
- Пароли для демо-аккаунтов эксперта/админа заведомо простые и находятся в
  этом README — только для локальной проверки решения, не для продакшена.
