# AskVUZ

Сервис вопросов-ответов в реальном времени для чат-бота МАХ: студент/абитуриент
выбирает вуз → выбирает категорию вопроса (Поступление, Учебный процесс, Заказ
справок и т.д.) → задаёт вопрос → вопрос маршрутизируется онлайн-специалисту
вуза, у которого есть подходящая роль и уровень репутации → ответ приходит в
тот же чат в реальном времени → ответ оценивается, отвечающему начисляются
баллы репутации, растёт его роль (от «Стажёра» до «Профи»).

Хакатон «Образовательные решения» (Минобрнауки России × МАХ), трек MVP для
МАХ. Полная идея и обоснование — в презентации (`docs/`, при наличии) и в
переписке по проекту; этот README описывает техническую часть.

## Архитектура

```
┌──────────────┐      webhook       ┌──────────────────────────┐
│   МАХ (бот)  │ ─────────────────▶ │        backend            │
│ мобильный/веб│ ◀───────────────── │ Express + Socket.IO        │
└──────────────┘   sendMessage       │  - conversation engine     │
                                      │  - маршрутизация вопросов  │
┌──────────────┐   REST + WS         │  - репутация / роли        │
│  frontend     │ ◀────────────────▶ │  - SQLite (better-sqlite3) │
│ (админ-панель │                     └──────────────────────────┘
│  + экспертный │
│  инбокс + чат-│
│  симулятор)   │
└──────────────┘
```

Ядро продукта — **`backend/src/conversation/engine.ts`**: конечный автомат
диалога (выбор вуза → категория → вопрос) один и тот же для обоих
транспортов:

- **реального МАХ** (`backend/src/max/webhook.ts` + `backend/src/max/client.ts`) —
  принимает вебхуки от МАХ, шлёт ответы через MAX Bot API;
- **браузерного чат-симулятора** (`backend/src/routes/simulator.ts`,
  `frontend/src/pages/ChatSimulator.tsx`) — тот же сценарий в браузере, без
  необходимости в реальном токене бота (см. ниже).

Только один пользовательский сценарий и одна бизнес-логика — отличается лишь
то, как сообщение "упаковывается" для конкретного транспорта.

Роли, у кого есть право отвечать (не любой пользователь), и очки репутации
описаны в `backend/src/reputation.ts` и `backend/src/types/index.ts`.
Маршрутизация вопроса подходящим онлайн-экспертам — в
`backend/src/routing/matcher.ts`.

## Быстрый старт (Docker)

```bash
cp .env.example .env
docker compose up --build
```

- Backend: http://localhost:4000 (REST API, health-check `/health`, MAX
  webhook `/webhook/max`)
- Frontend (админ-панель / экспертный инбокс / чат-симулятор):
  http://localhost:5173

При первом запуске (`SEED_ON_START=true` по умолчанию) backend автоматически
создаёт демо-данные: 2 тестовых вуза, категории вопросов, платформенного
администратора и экспертов на всех 6 ступенях роли. Список учёток — см.
[Тестовые учётные записи](#тестовые-учётные-записи).

Сборка обоих образов укладывается в лимит 5 минут (без учёта первой загрузки
базовых образов node:20-alpine / nginx:1.27-alpine).

> Данные хранятся в SQLite-файле в именованном Docker-томе `askvuz-db` —
> персистентны между перезапусками `docker compose up` (без `down -v`).

## Как проверить основной сценарий без токена МАХ

На момент сборки решения у команды не было развёрнутого рабочего токена
чат-бота МАХ (по правилам хакатона токен выдают организаторы отдельно —
Ограничения, п.9 брифа). Чтобы решение можно было полноценно проверить уже
сейчас, реализован **браузерный чат-симулятор**
(`http://localhost:5173/simulator`), который проходит **тот же самый**
пользовательский сценарий через **тот же самый backend-код**
(`conversation/engine.ts`), что и реальный МАХ-бот — разница только в
транспорте доставки сообщений. Это явно помеченный тестовый режим согласно
Ограничению п.10 брифа (`MOCK_MAX=true` по умолчанию).

1. Откройте http://localhost:5173/simulator, введите имя, нажмите «Начать чат».
2. Выберите вуз → категорию → напишите вопрос.
3. В другой вкладке войдите как эксперт (например `pro@itmo.demo` /
   `demo12345`) на http://localhost:5173/login → «Мои вопросы».
4. Возьмите вопрос в работу и ответьте — ответ мгновенно (через WebSocket)
   придёт обратно в чат-симулятор.
5. В чате оцените ответ («Решило вопрос», «Помогло», «Не помогло») — баллы
   репутации и роль эксперта обновятся сразу (видно на `/leaderboard`).

Это же самое можно повторить через `curl`/Postman — см. `openapi.yaml`.

## Подключение к МАХ

Когда организаторы выдадут рабочий токен бота:

1. В `.env` установите `MOCK_MAX=false` и `MAX_BOT_TOKEN=<токен>`.
2. Зарегистрируйте у МАХ webhook-адрес `https://<ваш-домен>/webhook/max`
   (опционально защитите его общим секретом через `MAX_WEBHOOK_SECRET` —
   backend проверяет заголовок `X-Max-Webhook-Secret`, если он задан).
3. Перезапустите backend.

**Важно:** пути `POST /messages` / `POST /answers` в
`backend/src/max/client.ts` и формат `update_type` в
`backend/src/max/webhook.ts` написаны по общепринятым конвенциям ботовых API
такого типа (message / callback / bot_started). Перед подключением реального
токена сверьте их с актуальной документацией MAX Bot API — сам бриф
специально предупреждает, что документация МАХ развивается и обновляется
(«Дополнительная информация», раздел «Сценарии работы платформы МАХ»).
Остальная часть системы (маршрутизация, репутация, БД, фронтенд) от этих
деталей не зависит и правки не потребует.

Мини-приложение (`frontend/`) — админ-панель и рабочее место эксперта —
подключается к чат-боту как надстройка, не как изолированный сервис
(Ограничение п.5 брифа), и работает как в мобильной, так и в веб-версии МАХ,
а также как обычная веб-страница вне МАХ (Ограничение п.3) — интеграция с
MAX Bridge (`frontend/src/maxBridge.ts`) сделана "мягко": если её нет,
приложение работает как обычный сайт.

## Роли и репутация

Отвечать могут не все — только верифицированные вузом пользователи
(`isAnswerer = true`), приглашённые через админ-панель. Роль растёт
автоматически по накопленным баллам репутации:

| Роль       | Мин. баллов | Комментарий                                             |
|------------|-------------|----------------------------------------------------------|
| Стажёр     | 0           | стартовая роль после верификации вузом                   |
| Помощник   | 50          |                                                            |
| Знаток     | 150         |                                                            |
| Эксперт    | 350         |                                                            |
| Наставник  | 700         |                                                            |
| **Профи**  | 1500        | высшая роль, ответ показывается как самый ценный          |

Начисление баллов (`backend/src/reputation.ts`):

- ответ отмечен «решило вопрос полностью» — **+25**
- ответ отмечен «помогло» — **+10**
- быстрый ответ (< 5 минут, настраивается `FAST_RESPONSE_THRESHOLD_SECONDS`) — **+5**
- ответ отмечен «не помогло» — **−5**

Категории вопросов сами задают минимальную роль для ответа
(`Category.minRole`), а «чувствительные» категории (например,
психологическая поддержка/безопасность) дополнительно доступны только
сотрудникам вуза (`isStaff = true`) — так продукт не подменяет
профессиональную помощь специалиста, а маршрутизирует к нему (рекомендация
№4 брифа). Сотрудников вуза администратор может продвинуть по ролям вручную,
это не отменяет автоматический рост по баллам для остальных отвечающих.

## Переменные окружения

См. `.env.example` в корне (для `docker compose`) и `backend/.env.example` /
`frontend/.env.example` (для запуска без Docker). Ключевые:

| Переменная            | Назначение                                                        |
|------------------------|--------------------------------------------------------------------|
| `MOCK_MAX`             | `true` (по умолчанию) — не звать реальный MAX Bot API, использовать чат-симулятор |
| `MAX_BOT_TOKEN`        | токен бота МАХ (выдают организаторы)                              |
| `MAX_WEBHOOK_SECRET`   | опциональный секрет для проверки входящих вебхуков                |
| `JWT_SECRET`           | секрет для подписи JWT (обязательно заменить вне локальной демонстрации) |
| `SEED_ON_START`        | заполнять ли БД демо-данными при старте контейнера                |
| `DATABASE_FILE`        | путь к файлу SQLite (в Docker — том `askvuz-db`)                  |

Секреты, токены и пароли нигде в коде не захардкожены — только читаются из
переменных окружения; `.env` — в `.gitignore`/`.dockerignore`, в репозиторий
передаётся только `.env.example` без реальных значений (Ограничение п.8).

## Локальная разработка без Docker

```bash
# backend
cd backend
cp .env.example .env
npm install
npm run seed   # заполнить демо-данными (один раз)
npm run dev    # http://localhost:4000

# frontend (в отдельном терминале)
cd frontend
cp .env.example .env
npm install
npm run dev    # http://localhost:5173
```

Backend хранит данные в `backend/data/askvuz.db` (SQLite-файл, создаётся
автоматически).

## Известные ограничения MVP

Указаны явно, как того требует Ограничение п.10 брифа:

- **Данные тестовые.** Оба вуза, все категории и все учётные записи
  экспертов — заранее подготовленные демо-данные (`backend/src/db/seed.ts`),
  а не выгрузка из реальной системы вуза.
- **Интеграция с МАХ подготовлена, но не подключена к реальному боту** —
  причина исключительно в отсутствии токена на момент сборки решения (токен
  выдают организаторы отдельно). Код вебхука и клиента написан и готов к
  подключению — см. [«Подключение к МАХ»](#подключение-к-мах).
- Нет интеграции с реальными системами вуза (деканат/1С) — она вне рамок
  MVP согласно рекомендациям брифа («сначала определите пользовательскую
  задачу», а не стройте лишние интеграции).
- Пароли для демо-аккаунтов эксперта/админа заведомо простые и находятся в
  этом README — только для локальной проверки решения, не для продакшена.
