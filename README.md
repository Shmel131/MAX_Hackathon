
# AskVUZ — сервис вопросов и ответов в реальном времени для чат-бота МАХ

**Хакатон «Образовательные решения» (Минобрнауки России × MAX).**

AskVUZ соединяет студентов (и, в перспективе, абитуриентов) с верифицированными
сотрудниками вуза: студент выбирает вуз и категорию обращения, задаёт вопрос,
система маршрутизирует его специалисту с подходящей ролью и категорией доступа,
ответ приходит в реальном времени. Диалог можно продолжать (уточняющие
вопросы), затем оценить и закрыть обращение. По оценке студента отвечающему
начисляются **очки репутации**, от которых зависит его роль:
Помощник → Знаток → Профи.

> **Терминология.** В пользовательском интерфейсе и в документации используется
> единое название — **очки репутации**. В коде и в API исторически сохранено
> внутреннее имя того же показателя: поле `aura` / таблица `aura_events`
> (`backend/src/db/models.ts`, `backend/src/reputation.ts`). Это один и тот же
> показатель, а не две разные метрики.

| Порты | backend — `4000`, frontend — `5173` |
| Документация API | `openapi.yaml` (OpenAPI 3.0.3), `DATA-API.yaml` (машиночитаемый набор проверок) |
| Демо-данные | загружаются автоматически при первом старте (`SEED_ON_START=true`) |
| Реальный токен MAX | на момент сборки не выдан; интеграция реализована и готова к подключению, по умолчанию работает тестовый режим `MOCK_MAX=true` (см. [Запуск в МАХ](#запуск-в-мах)) |

**Что важно знать перед проверкой:**

1. Решение запускается одной командой из Docker Compose и не требует ручной
   подготовки базы данных или установки внешних сервисов.
2. Веб-приложение и бот используют **один и тот же** бизнес-логический слой
   (`backend/src/conversation/engine.ts`), поэтому полный пользовательский
   сценарий можно проверить через браузер, не дожидаясь токена MAX.
3. Все учётные данные демо-пользователей перечислены в разделе
   [Тестовые учётные записи](#тестовые-учётные-записи); вход студента выполняется
   по имени и создаёт запись автоматически.
4. Начисление очков репутации происходит **только** по итогам оценки ответа
   студентом — это видно в реальном времени на странице «Рейтинг».

## Архитектура

```
┌──────────────┐      webhook       ┌───────────────────────────────┐
│   MAX (бот)  │ ─────────────────▶ │            backend            │
│ мобильный/веб│ ◀───────────────── │ Express + Socket.IO           │
└──────────────┘   sendMessage      │  - conversation engine (wizard)│
                                    │  - треды вопросов и сообщений │
┌──────────────┐  REST + WebSocket  │  - маршрутизация по роли      │
│   frontend   │ ◀────────────────▶ │  - очки репутации / роли      │
│ - ЛК студента│                    │  - SQLite (better-sqlite3)    │
│ - инбокс     │                    └───────────────────────────────┘
│   отвечающего│
│ - админ-панель│
│ - рейтинг    │
└──────────────┘
```

Ядро продукта — `backend/src/conversation/engine.ts`: визард выбора
вуза → категории → текста вопроса, общий для обоих транспортов:

- **реального MAX** (`backend/src/max/webhook.ts` + `backend/src/max/client.ts`);
  студент в MAX не выполняет вход — его запись `Student` создаётся
  автоматически по `sender.user_id` платформы;
- **веб-приложения** (`backend/src/routes/student.ts` →
  `frontend/src/pages/AskQuestion.tsx`) — тот же визард, вход по имени
  (см. [«Как войти»](#как-войти) и [ограничения MVP](#известные-ограничения-mvp-и-план-развития)).

После создания обращения вся дальнейшая переписка (ответ специалиста,
уточняющие вопросы, повторные ответы) ведётся в треде сообщений
(`backend/src/db/store.ts`, таблица `messages`), а не внутри визарда, — поэтому
и диалог в MAX, и веб-кабинет одинаково поддерживают продолжение разговора.

## Быстрый старт (Docker)

Требования: Docker Engine ≥ 20.10 и Docker Compose v2.

```bash
cp .env.example .env
docker compose up --build
```

(для запуска в Ubuntu может понадобиться sudo перед docker)

- **Backend:** http://localhost:4000 — REST API (`/api/...`), проверка
  доступности `/health`, webhook MAX `/webhook/max`
- **Frontend:** http://localhost:5173

При первом запуске (`SEED_ON_START=true` по умолчанию) backend автоматически
создаёт демо-данные: два вуза, категории обращений, платформенного
администратора и отвечающих на всех трёх ступенях роли. Список учётных записей —
[Тестовые учётные записи](#тестовые-учётные-записи).

Для остановки и полной очистки демонстрационных данных:

```bash
docker compose down -v
rm -f backend/data/askvuz.db   # если требуется чистая база при следующем старте
```

## Как войти

Приложение различает два независимых типа входа.

**Студент** — на главной странице (`/`) вводит только имя. Это создаёт
(или при повторном входе тем же именем находит существующую) запись `Student`
и выдаёт JWT-токен, сохраняемый в браузере. Отдельного пароля у студента в MVP
нет — см. [ограничения MVP](#известные-ограничения-mvp-и-план-развития).

**Сотрудник вуза** (отвечающий, администратор вуза, платформенный
администратор) входит по e-mail и паролю на странице `/login`; ссылка «Войти»
доступна в шапке на любой странице и внизу формы входа студента.

Учётные данные нового сотрудника создаются один раз и показываются в интерфейсе
сразу после создания аккаунта:

- когда платформенный администратор подключает новый вуз (раздел
  «Платформенный админ» в админ-панели) — вместе с вузом создаётся его первый
  администратор, e-mail и временный пароль выводятся в том же окне;
- когда администратор вуза приглашает нового отвечающего (раздел
  «Пригласить нового отвечающего») — e-mail и временный пароль выводятся сразу
  после отправки формы.

В обоих случаях это демонстрационный режим: в продуктовой версии временный
пароль отправлялся бы приглашением на почту, а не отображался в интерфейсе.

## Проверка решения за 5 минут

Рекомендуемый маршрут для проверяющих (не требует токена MAX):

1. `docker compose up --build`, дождаться статуса `healthy` у сервиса backend.
2. Открыть http://localhost:5173, ввести любое имя — откроется личный кабинет
   студента.
3. «Задать вопрос» → выбрать вуз «ИТМО (демо)» → категорию → сформулировать
   вопрос → отправить.
4. В другой вкладке (или другом браузере) войти на `/login` как отвечающий
   `pro@itmo.demo` / `demo12345` → «Мои вопросы» → раздел «Новые» → взять
   обращение в работу и ответить. Ответ появится у студента без перезагрузки
   страницы (Socket.IO).
5. Вернуться во вкладку студента: написать уточняющий вопрос, получить ответ,
   оценить его («Решило вопрос»), при необходимости закрыть обращение.
6. Открыть «Рейтинг» и убедиться, что очки репутации отвечающего выросли, а при
   пересечении порога изменилась роль.
7. Войти как `admin@askvuz.local` / `admin12345` (подключить новый вуз) и как
   `uniadmin@itmo.demo` / `demo12345` (добавить категорию, пригласить
   отвечающего, посмотреть матрицу «Роли и доступ к категориям»).
8. Сверить контракты запросов с `openapi.yaml` и выполнить проверки из
   `DATA-API.yaml` (например, `curl http://localhost:4000/health`).

Ожидаемый результат: полный цикл «вопрос → маршрутизация → ответ → уточнение →
оценка → начисление очков репутации → закрытие» воспроизводится без ручных
правок базы данных.

## Пользовательские сценарии

**Студент** (по умолчанию, без отдельной регистрации): открывает сервис →
вводит имя → видит две кнопки: «Задать вопрос» и «Мои вопросы».

*Задать вопрос* — визард: вуз → категория → текст вопроса. После отправки
студент может сразу перейти в «Мои вопросы».

*Мои вопросы* — личный кабинет: список всех обращений студента со статусами
«Ожидает специалиста», «Взят в работу», «Есть ответ», «Закрыт». Открыв
обращение, студент видит весь тред сообщений и может:

- написать уточняющий вопрос специалисту (диалог продолжается);
- оценить ответ («Решило вопрос» / «Помогло» / «Не помогло») — оценка начисляет
  отвечающему очки репутации;
- закрыть обращение кнопкой «Закрыть вопрос», если оно больше не актуально:
  обращение исчезает из очереди отвечающих, переписка блокируется.

**Отвечающий (эксперт)**: вход на `/login` → «Мои вопросы» → два списка:
«Новые» (доступные его роли и категории, ещё не взятые в работу) и «В работе
у вас» (взятые им, независимо от статуса). Обращение можно взять в работу и
отвечать — в том числе на уточняющие вопросы студента; диалог идёт в том же
треде.

**Администратор вуза**: подключает категории обращений, приглашает отвечающих,
вручную назначает роль, может удалить отвечающего (аккаунт деактивируется —
переписка и накопленные очки репутации сохраняются) или категорию, просматривает
матрицу доступов.

**Платформенный администратор**: подключает новые вузы к сервису; при
подключении вуза сразу создаётся учётная запись его администратора.

**Рейтинг** — публичная страница (доступна студентам и посетителям без входа):
выбор вуза → таблица отвечающих с их ролью и очками репутации. У студента и
анонимного посетителя по умолчанию открыт первый вуз из списка, у вошедшего
сотрудника — собственный вуз.

## Роли и очки репутации

Отвечать могут только верифицированные вузом пользователи
(`isAnswerer = true`), приглашённые через админ-панель. Роль растёт
автоматически по накопленным очкам репутации:

| Роль | Минимум очков репутации | Комментарий |
|---|---|---|
| Помощник (`HELPER`) | 0 | стартовая роль после верификации вузом |
| Знаток (`KNOWER`) | 150 | |
| Профи (`PRO`) | 600 | высшая роль, ответ считается наиболее ценным |

Пороги заданы в `ROLE_THRESHOLDS` (`backend/src/types/index.ts`), лестница —
в `ROLE_LADDER`.

Начисление очков репутации (`backend/src/reputation.ts`, константы `AURA`)
происходит **только** в момент оценки ответа студентом
(`POST /api/student/questions/{id}/rate`) — сам факт ответа ничего не начисляет:

- «решило вопрос полностью» — **+25** (`ANSWER_RESOLVED`)
- «помогло» — **+10** (`ANSWER_HELPFUL`)
- дополнительно, если первый ответ поступил быстрее порога
  (`FAST_RESPONSE_THRESHOLD_SECONDS`, по умолчанию 300 секунд) и студент выбрал
  «решило»/«помогло» — **+5** (`FAST_RESPONSE_BONUS`)
- «не помогло» — **−5** (`ANSWER_NOT_HELPFUL`)

В таблице также зарезервированы значения для сценариев, которые появятся после
подключения модерации: отклонение ответа модерацией — **−15**
(`ANSWER_REJECTED_BY_MODERATION`), жалоба на ответ — **−10** (`COMPLAINT`).

Очки репутации не опускаются ниже нуля (`Math.max(0, …)`), каждое начисление
фиксируется в журнале `aura_events` с указанием причины, что обеспечивает
прозрачность и пересчитываемость рейтинга. Роль сотрудника со статусом
`isStaff = true` понижается только до роли, назначенной вузом вручную:
автоматический пересчёт не может опустить официального сотрудника ниже
установленной вузом ступени.

### Доступ к категориям

Действуют два независимых правила, оба обязательны:

1. **Минимальная роль категории** (`Category.minRole`) — порог по лестнице
   Помощник → Знаток → Профи. Роль выше порога также подходит: Профи видит все
   категории своего вуза.
2. **Признак конфиденциальности** (`Category.isSensitive`) — по умолчанию
   выключен; включён для категории психологической поддержки и безопасности.
   Такие обращения видят только сотрудники вуза (`isStaff = true`) — даже если
   волонтёр уже достиг роли Профи по очкам репутации, доступ к чувствительным
   обращениям требует официального статуса сотрудника, который назначается
   вузом вручную при приглашении, а не активностью.

Это две ортогональные шкалы, а не одна: «сколько обращений успешно закрыто»
(очки репутации и роль) и «официальный ли статус сотрудника вуза» (`isStaff`)
измеряют разные вещи. Итоговая матрица по конкретному вузу доступна в
админ-панели, раздел «Роли и доступ к категориям».

## Маршрутизация обращений

Логика подбора отвечающего сосредоточена в `backend/src/routing/matcher.ts`
(`findEligibleExperts`) и выполняется в момент создания обращения:

1. Обращение ограничивается вузом, выбранным студентом в визарде.
2. Кандидаты — сотрудники вуза с флагами `isAnswerer = 1` и `isActive = 1`
   (деактивированные администратором исключаются автоматически).
3. Фильтр по доступу к категории: `roleAtLeast(роль сотрудника, category.minRole)`,
   а для категорий с `isSensitive = 1` дополнительно `isStaff = 1`.
4. Подходящие отвечающие ранжируются по убыванию накопленных очков репутации —
   выше в списке тот, кто отвечает лучше; для конфиденциальных категорий обращение
   создаётся сразу со статусом `ESCALATED`.
5. Итоговый список отдаётся всем имеющим доступ сотрудникам как очередь «Новые»:
   отвечающий сам берёт обращение в работу (`POST /api/questions/{id}/claim`).
   Модель self-service выбрана осознанно: она не требует графика смен и устойчива
   к отсутствию дежурного, а ранжирование по очкам репутации подсказывает, кому
   обращение стоит взять первым.

События realtime рассылаются Socket.IO. При подключении клиент передаёт JWT в
`handshake.auth.token`, после проверки попадает в комнату `university:{id}`
(сотрудник) или `student:{id}` (студент) и получает события:
`question:new` (новое обращение), `question:claimed` (взято в работу),
`question:message` (новое сообщение в треде), `question:closed` (обращение
закрыто). За счёт этого очереди отвечающих и тред студента обновляются без
опроса сервера; при недоступности WebSocket доступен обычный REST-цикл.

SQLite, WAL-режим и внешние ключи включены; схема создаётся автоматически при

## Запуск в МАХ

1. В `.env` установить `MOCK_MAX=false` и `MAX_BOT_TOKEN=<токен>`.
2. Зарегистрировать в MAX адрес вебхука `https://<ваш-домен>/webhook/max`
   (при желании защитить его общим секретом через `MAX_WEBHOOK_SECRET`).
3. Перезапустить backend.

Пути `POST /messages` / `POST /answers` в `backend/src/max/client.ts` и формат
`update_type` в `backend/src/max/webhook.ts` написаны по общепринятым конвенциям
ботовых API такого типа — перед подключением реального токена их следует сверить
с актуальной документацией MAX Bot API. Остальная часть системы (маршрутизация,
очки репутации, база данных, фронтенд) от этих деталей не зависит.

В MAX студент не выполняет отдельный вход: его запись `Student` создаётся
автоматически по `sender.user_id` платформы
(`students.findOrCreateByMaxUserId` в `backend/src/db/store.ts`). Экран «войдите
по имени» относится только к веб-версии.

## Безопасность

- Пароли сотрудников хранятся в виде хешей bcrypt, в открытом виде не
  сохраняются и не логируются.
- Доступ к API — по JWT; авторизация и разграничение прав сосредоточены в
  `backend/src/middleware/auth.ts`: студент видит только собственные обращения,
  отвечающий — доступные ему по роли и категории, администратор вуза — только
  свой вуз, платформенный администратор — все вузы.
- Входные данные всех эндпоинтов проверяются схемами `zod`.
- Конфиденциальные категории защищены признаком `isStaff`, а не только
  накопленными очками репутации.
- Деактивация сотрудника не удаляет историю переписки и начисленные очки
  репутации (сохраняется аудируемость).
- Секреты только в переменных окружения; `.env` не попадает в репозиторий и в
  образы (`dockerignore`).
- Для production-развёртывания необходимо задать `JWT_SECRET`,
  `ADMIN_PASSWORD`, ограничить `CORS_ORIGIN` и включить `MAX_WEBHOOK_SECRET`.

## Известные ограничения MVP и план развития

- **Вход студента по имени, без пароля.** Повторный вход тем же именем (без
  учёта регистра) находит существующую запись `Student`, постоянство сессии
  обеспечивает JWT-токен в браузере. В продуктовой версии предусмотрен вход по
  логину/паролю либо автоматическая идентификация по `user_id` платформы —
  последний вариант уже реализован для канала MAX
  (`students.findOrCreateByMaxUserId`).
- **Демо-интеграция с MAX подготовлена, но не подключена к реальному боту** —
  на момент сборки решения рабочий токен не был выдан. Код вебхука и клиента
  написан и готов к запуску, см. [«Запуск в МАХ»](#запуск-в-мах).
- **Данные тестовые.** Оба вуза, все категории и учётные записи отвечающих
  подготовлены сид-скриптом (`backend/src/db/seed.ts`).
- **Одна роль заявителя.** Обратная связь рассчитана на студента; роль
  «абитуриент» в MVP не реализована.
- **Базовая модерация.** `backend/src/moderation.ts` фильтрует явный спам;
  постоянного чёрного списка студентов и лимита «не более N обращений в час»
  пока нет.
- **Нет интеграции с внутренними системами вуза** (деканат, 1С).
- **Простые пароли демо-учётных записей** приведены в этом README исключительно
  для локальной проверки решения и не предназначены для продакшена.
- **SQLite как единственное хранилище** — осознанный выбор для MVP: отсутствие
  внешней СУБД упрощает проверку. Схема изолирована в репозиторном слое
  (`backend/src/db/store.ts`), поэтому переход на PostgreSQL сводится к замене
  этого слоя.

План развития: полноценная аутентификация студентов в веб-канале (логин/пароль
или OAuth через платформу), SLA-таймеры и эскалация обращений без ответа,
статистика загрузки по категориям для администратора вуза, расширенная
модерация (чёрный список студентов, лимит «не более N обращений в час»),
роль абитуриента, live-обновление рейтинга по WebSocket, миграция на PostgreSQL
и горизонтальное масштабирование с sticky-сессиями Socket.IO.

## Где хранятся данные

Backend хранит все данные (вузы, категории, студентов, обращения, сообщения,
очки репутации) в одном файле SQLite, без внешней СУБД.

- **В Docker:** путь внутри контейнера — `/app/data/askvuz.db`; он монтируется
  на хост в `docker-compose.yml` как `./backend/data/askvuz.db`. После
  `docker compose up` в папке проекта появляется файл `backend/data/askvuz.db`,
  который можно открыть напрямую (например, в «DB Browser for SQLite» или
  командой `sqlite3 backend/data/askvuz.db`).
- **Без Docker** (`npm run dev` в `backend/`): файл лежит там же —
  `backend/data/askvuz.db`, создаётся автоматически при первом запуске.
- Путь настраивается переменной окружения `DATABASE_FILE`
  (`backend/src/db/connection.ts`).
